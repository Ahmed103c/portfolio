Problématiques

Ce projet répond à deux problématiques concrètes :

Problématique 1

Comment déployer une application sur internet de manière automatisée et reproductible ?

Problématique 2

Comment passer d'une version à l'autre sans interruption de service ?

L'application

L'application permet à plusieurs utilisateurs de modifier les pixels d'une grille partagée. Elle est composée d'un frontend React, d'un backend ASP.NET Core et d'une base de données PostgreSQL. L'ensemble a d'abord été développé et testé localement avant d'être déployé sur AWS.

Application développée et testée localement

Architecture cible sur AWS

L'objectif était de créer deux environnements séparés et isolés :

Indus

Environnement d'intégration avec 1 master + 1 worker

Prod

Environnement de production avec 1 master + 2 workers

La base de données PostgreSQL est hébergée sur une instance RDS AWS managée, séparée des EC2. Ce choix s'impose car les instances EC2 t3.small du free tier sont limitées en mémoire — faire tourner PostgreSQL dedans aurait compromis les performances de l'application.

Architecture de la solution sur AWS

Pipeline CI/CD

L'objectif est d'avoir une pipeline GitHub Actions qui automatise entièrement les déploiements :

Push sur main
→
Build automatique des images Docker + déploiement sur l'environnement indus
PR mergée vers prod
→
Déploiement automatique sur l'environnement de production

Cette approche garantit que la production ne reçoit jamais de code non validé sur indus.

Implémentations

Infrastructure as Code — Terraform

L'intégralité de l'infrastructure AWS est provisionnée automatiquement : VPC, subnets, Security Groups, instances EC2, base de données RDS PostgreSQL et Elastic IPs. Aucun clic dans la console AWS n'est nécessaire pour recréer l'infrastructure depuis zéro.

Configuration automatisée — Ansible

L'installation et la configuration de K3s sur les instances EC2 est entièrement automatisée via des playbooks Ansible. Cela inclut la configuration réseau spécifique à AWS (interface ens5, certificats TLS, désactivation de Traefik).

Conteneurisation — Docker

Les deux applications sont conteneurisées avec des Dockerfiles multi-stage optimisés, minimisant la taille des images finales.

Orchestration — K3s

Les applications tournent dans un cluster Kubernetes léger (K3s). Le routing du trafic est géré par un pod Nginx en mode hostNetwork qui sert de point d'entrée unique sur le port 80.

Deux environnements séparés

Chaque environnement possède son propre cluster K3s et sa propre base de données PostgreSQL isolée sur le même RDS.

Pipeline CI/CD — GitHub Actions

Build, push sur Docker Hub et déploiement entièrement automatisés selon la branche.

Observabilité — Prometheus & Grafana

Le backend expose ses métriques via OpenTelemetry, collectées par Prometheus et visualisées dans Grafana. Les health checks permettent à K3s de redémarrer automatiquement les pods défaillants.

Défis techniques résolus

Le principal défi a été la configuration réseau de K3s sur AWS. Deux problèmes majeurs se sont présentés :

⚠️

Problème 1 — Interface réseau

AWS nomme son interface réseau ens5 et non eth0 comme sur un serveur classique. Sans cette configuration, Flannel (le réseau overlay de K3s) refusait de démarrer.

⚠️

Problème 2 — Traefik v3

La version de K3s installée incluait Traefik v3 qui présentait un bug avec Flannel — les requêtes HTTP ne passaient jamais. Cela nous a amenés à implémenter une solution alternative.

⚠️

URLs hardcodées dans React

En développement, l'URL du backend était http://localhost:7009/api/pixels — impossible à utiliser en production. La solution : utiliser des URLs relatives /api/pixels dans React et laisser Nginx faire le routing vers le bon service selon le chemin.

✅

La solution — Nginx hostNetwork

Au lieu de Traefik, on utilise un pod Nginx configuré avec hostNetwork: true. Cela permet au pod de bypasser complètement le réseau K3s et de binder directement sur le port 80 de l'EC2.

Observabilité — Prometheus & Grafana

Le backend .NET expose ses métriques via OpenTelemetry sur l'endpoint /metrics, et des health checks sur /health.

Prometheus et Grafana sont installés via Helm dans un namespace dédié monitoring, séparé du namespace default où tourne l'application. Cette séparation garantit que si le monitoring plante, l'application continue de fonctionner.

Un ServiceMonitor fait le lien entre Prometheus et le backend — il indique à Prometheus quel service scraper, sur quel chemin et à quelle fréquence (toutes les 15 secondes).
